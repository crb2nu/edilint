# EL1004 — charset.zero-width

| Class | Severity | Applies to |
|---|---|---|
| charset | error | `all` |

Zero-width or bidirectional formatting character that renders as nothing but occupies bytes.

## What it catches

Zero-width spaces, zero-width joiners and the bidirectional formatting controls. They render as nothing, so a field looks correct in every editor while comparing unequal to the same field without them — the reason an identifier match fails on one side of an integration and not the other.

## Example

`eligibility.psv`:

```text
HDR|NORTHGATE HEALTH|20260115|ELIG
DTL|NGH9000\u200b00001|RIVERA|DANA|19840322|F|PPO-GOLD|20260101|20261231
```

The escape sequences above stand for the bytes the file holds literally.

`edilint eligibility.psv` reports:

```text
eligibility.psv:2:12: error: [EL1004 charset.zero-width] invisible character ZERO WIDTH SPACE (U+200B); it renders as nothing but occupies bytes and shifts fixed-width offsets (record 2, type DTL) https://crb2nu.github.io/edilint/rules/EL1004.html
```

## How to fix

Delete the character. Because it is invisible, delete it by code point rather than by eye: match the reported column, or filter the file for the code point the finding names.

## When to suppress

There is no routine case. A zero-width character is never load-bearing in an interchange field, so a finding here is a defect in whatever produced the file.

Suppress the rule for a run with `edilint --disable EL1004`, or for a repository by listing it under `disable:` in `.edilint.yml`.
