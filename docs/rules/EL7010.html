EL7010

edifact.duplicate-control-reference

Applies to: edifact

What it catches and why it matters

A UNB-5 interchange reference repeats within the file, a UNG-5 group reference repeats within its interchange, or a UNH-1 message reference repeats within its functional group, or within its interchange when no groups are used.

Failing example

These synthetic fragments illustrate the defect; they are not complete interchange files. Backslash escapes name bytes such as \r (CR) and \n (LF).

UNH+1+ORDERS:D:96A:UN'...UNT+3+1'UNH+1+ORDERS:D:96A:UN'  (UNH-1 repeated in one interchange)

How to fix it

Assign a fresh UNB-5 per interchange in the file, UNG-5 per group in the interchange, and UNH-1 per message in the group or interchange.

False positives and limits

Restarting UNH-1 per interchange or per group is valid and is not reported. Concatenating two copies of the same interchange into one file does repeat UNB-5; send them as separate files if that is intended.

Acknowledgments and suppression

Related acknowledgment codes (apply only to the described defect):
  CONTRL code 26 (UCI.0085): duplicate interchange reference detected
  CONTRL code 26 (UCF.0085): duplicate group reference detected within the interchange
  CONTRL code 26 (UCM.0085): duplicate message reference detected within the group or interchange
CONTRL references use syntax-error element 0085, not action element 0083. UCI, UCF and UCM report interchange, group and message service-segment errors respectively. A missing or unreadable header can prevent a valid CONTRL response. Truncation, orphaned envelopes and data outside an interchange have no single mapping here.
Sources: https://service.gefeg.com/jwg1/Archive/v3/mt/m01.htm https://service.gefeg.com/jwg1/Archive/cl/v3/21a/cl16.htm
Suppress the rule with --disable EL7010, or list it under "disable" in .edilint.yml. To accept the occurrences a file already has without suppressing the rule, record them with --write-baseline and run with --baseline.
