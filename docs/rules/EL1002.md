# EL1002 — charset.invalid-utf8

| Class | Severity | Applies to |
|---|---|---|
| charset | error | `all` |

Byte sequence is not valid UTF-8.

## What it catches

Any byte sequence that is not well-formed UTF-8, which in practice means a file encoded in a single-byte code page — Latin-1 or CP1252 — that was passed on as if it were UTF-8. When the input is dense enough in invalid bytes and NULs not to be text at all, the rule reports once and the interchange checks are skipped.

## Example

`eligibility.psv`:

```text
HDR|NORTHGATE HEALTH|20260115|ELIG
DTL|NGH900000001|RIVERA\xff|DANA|19840322|F|PPO-GOLD|20260101|20261231
```

The escape sequences above stand for the bytes the file holds literally.

`edilint eligibility.psv` reports:

```text
eligibility.psv:2:24: error: [EL1002 charset.invalid-utf8] invalid UTF-8 byte 0xFF; the file is not valid UTF-8 and byte-oriented parsers will disagree with text-oriented ones about field boundaries (record 2, type DTL) https://crb2nu.github.io/edilint/rules/EL1002.html
```

## How to fix

Transcode the file from its real encoding rather than editing the offending bytes. `iconv -f windows-1252 -t utf-8` covers the usual case; fix the generator afterwards so the next file is emitted as UTF-8.

## When to suppress

There is no safe case. A file that is not valid UTF-8 cannot be read consistently by two different parsers, so the finding always describes a genuine ambiguity.

Suppress the rule for a run with `edilint --disable EL1002`, or for a repository by listing it under `disable:` in `.edilint.yml`.
