# EL7010 — edifact.duplicate-control-reference

| Class | Severity | Applies to |
|---|---|---|
| edifact | error | `edifact` |

A UNB-5 interchange reference repeats within the file, a UNG-5 group reference repeats within its interchange, or a UNH-1 message reference repeats within its functional group, or within its interchange when no groups are used.

Trading partners report this defect with:

| Acknowledgment | Element | Code | Meaning |
|---|---|---|---|
| CONTRL | `UCI.0085` | `26` | duplicate interchange reference detected |
| CONTRL | `UCF.0085` | `26` | duplicate group reference detected within the interchange |
| CONTRL | `UCM.0085` | `26` | duplicate message reference detected within the group or interchange |

## What it catches

A control reference repeated within its scope: a UNB-5 interchange reference used twice in one file, a UNG-5 group reference used twice in one interchange, or a UNH-1 message reference used twice in one functional group, or in one interchange when it has no groups. Receivers use these references to detect resent data, so a repeat is rejected as a duplicate (CONTRL code 26) or silently dropped. The finding is on the repeating header and names the record that first used the reference.

## Example

`order.edi`:

```text
UNA:+.? '
UNB+UNOA:4+NORTHGATEHEALTH+VALEMEDGROUP+260115:1430+NG260002'
UNH+NG0001+ORDERS:D:96A:UN'
BGM+220+NG77001+9'
UNT+3+NG0001'
UNH+NG0001+ORDERS:D:96A:UN'
BGM+220+NG77002+9'
UNT+3+NG0001'
UNZ+2+NG260002'
```

`edilint order.edi` reports:

```text
order.edi:6: error: [EL7010 edifact.duplicate-control-reference] UNH-1 control reference "NG0001" is already used by record 2 in this interchange; control references must be unique within their scope (record 5, type UNH) https://crb2nu.github.io/edilint/rules/EL7010.html
```

## How to fix

Have the sending system assign a fresh reference to every interchange, group and message, and keep the trailer reference matched to its header.

## When to suppress

A sender that restarts UNH-1 at 1 in every interchange or group is valid and is not reported, because the scope ends at the enclosing interchange or group. Within one scope there is no safe case.

Suppress the rule for a run with `edilint --disable EL7010`, or for a repository by listing it under `disable:` in `.edilint.yml`.
